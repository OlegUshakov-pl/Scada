# Задание: Simulator виртуальных устройств для SCADA constructor

## Цель
Генерировать тестовые показания для нескольких устройств одновременно (сейчас — один датчик костылём), **не смешивая симулятор с реальными Device**.

## Ключевое ограничение (важно!)
`SimulatorDevice` — отдельная модель/таблица, ссылается на `Device` через `ForeignKey`, но **не заменяет и не расширяет** его.
Эмулятор **не пишет** напрямую в `Device.value`.
Сгенерированное значение должно попадать в систему **тем же путём**, каким в будущем будут приходить реальные данные от драйверов (Modbus/OPC UA, C3) — т.е. через тот же endpoint / очередь / Redis-канал / callback, который слушает Rules-движок и логика между Django и FastAPI.

→ Практическая инструкция для AI-агента: **сначала найти в текущем кодовой базе точку входа**, через которую реальный драйвер сообщает системе "у устройства X новое значение Y" (вероятно FastAPI endpoint, либо Redis pub/sub топик, либо внутренняя функция/celery-задача, которую дергает драйвер). Эмулятор должен вызывать **ту же самую точку входа**, а не дублировать логику записи в БД в обход неё. Если такой единой точки входа ещё нет — она должна появиться как побочный эффект этой задачи (рефакторинг: и реальный путь, и симулятор идут через одну функцию/эндпоинт).

## Приложение
Новое Django-приложение `emulator`.

## Модель `SimulatorDevice`

| Поле | Тип | Описание |
|---|---|---|
| `device` | `ForeignKey(Device)` | реальное устройство, показания которого эмулируются |
| `signal_type` | `CharField` (choices) | `temperature` / `pressure` / `digital_input` / `motor` |
| `mode` | `CharField` (choices) | `constant` / `random` / `sine` / `ramp` / `cycle` |
| `min_value` | `FloatField` | нижняя граница диапазона |
| `max_value` | `FloatField` | верхняя граница диапазона |
| `period` | `FloatField` | период в секундах (для sine/ramp/cycle) |
| `update_interval` | `FloatField` | как часто генерировать новое значение, сек |
| `enabled` | `BooleanField` | вкл/выкл конкретный симулятор без удаления записи |

## Логика генераторов (для справки, можно менять формулы)

- **constant** — всегда `min_value` (или отдельное фиксированное значение)
- **random** — `random.uniform(min_value, max_value)` на каждый тик
- **sine** — синусоида между `min_value` и `max_value` с периодом `period`
- **ramp** — линейный рост от `min_value` до `max_value` за `period`, затем сброс в начало
- **cycle** — циклический перебор фиксированного набора значений (например, для `digital_input`: 0/1/0/1)

Реализация должна быть **stateless по времени** (на основе `time.time() % period`), чтобы не хранить промежуточное состояние и переживать рестарт процесса без проблем.

## Планировщик
Каждый активный `SimulatorDevice` тикает по своему `update_interval` независимо от других (не общий глобальный tick для всех). Механизм на усмотрение реализации: отдельные потоки/asyncio-таски/celery beat с разными интервалами — главное, что 10 устройств с разными `update_interval` не блокируют друг друга.

## Что НЕ делать
- Не добавлять поля симуляции в саму модель `Device`.
- Не писать значение в БД `Device.value` напрямую из эмулятора.
- Не создавать отдельный API/канал только "для симуляции" — путь должен быть общим с реальными данными.
