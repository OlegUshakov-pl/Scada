# Задание: интеграция SCADA screen constructor в Django-проект

## Контекст

Есть рабочий React-прототип редактора мнемосхем (конструктор экранов SCADA, аналог редактора схем в Rapid SCADA или Perspective Designer в Ignition):

- Палитра слева с категориями виджетов, drag-and-drop на канвас
- Канвас с сеткой (grid), позиционирование по x/y, resize за угловые хендлы, rotation
- Панель свойств справа: привязка тега (сейчас — выбор из захардкоженного списка строк), цвет, текст label, поворот
- Preview-режим — переключает в режим "live sim", значение тега обновляется раз в секунду поллингом с фронта; во время Preview редактирование заблокировано
- Внизу — живой JSON модели экрана (widgets array)
- Кнопка Save — сейчас просто делает `console.log` модели, реального сохранения нет

Стек проекта, в который встраиваем: **Django + FastAPI + Redis + TimescaleDB**. FastAPI обслуживает логику устройств и драйверы (Modbus/OPC UA и др.), у Django — основная бизнес-логика и модели устройств.

Прототип прилагается отдельным файлом (React-компонент/HTML-артефакт).

## Задача

Встроить прототип как полноценный модуль редактора экранов в Django-проект: с персистентностью экранов, реальными тегами вместо строк-заглушек, и живыми данными через WebSocket вместо клиентского поллинга.

## 1. Модель данных (Django)

- `Screen`: `id`, `name`, `width`, `height`, `created_at`, `updated_at`
- Виджеты экрана хранить **как JSONField внутри `Screen`** (`widgets = JSONField()`), НЕ выносить в отдельную нормализованную таблицу на этом этапе — формат виджета ещё не стабилизировался, нормализация усложнит итерацию без пользы на v1.
- Формат виджета в JSON поменять: вместо `tag: "строка"` — `{tag_id, device_id}`, где `device_id` — ссылка на существующую модель `Device` (или её эквивалент в проекте).

## 2. API (Django REST Framework)

- `GET /api/screens/` — список экранов
- `GET /api/screens/{id}/` — экран целиком с массивом widgets
- `POST /api/screens/` — создание нового экрана
- `PATCH /api/screens/{id}/` — сохранение изменений (заменить текущий console.log на реальный вызов этого эндпоинта)
- `GET /api/devices/` (или `/api/tags/`) — список доступных тегов/устройств для панели свойств, чтобы select в UI подтягивал реальные данные, а не захардкоженный список

## 3. Живые данные — замена поллинга

Сейчас Preview дёргает значение раз в секунду с фронта (клиентский setInterval). Это нужно заменить:

- Значения тегов публикуются в Redis (pub/sub) слоем логики устройств на стороне FastAPI
- Фронт подписывается на обновления через WebSocket — либо через Django Channels (если Channels уже используется в проекте), либо через отдельный WS-эндпоинт на FastAPI, поскольку логика устройств уже там
- Формат сообщения — дельты, не полный снапшот: `{tag_id: value, ...}`
- Preview-режим на фронте должен просто подписываться на нужные tag_id виджетов текущего экрана, а не поллить их по одному

## 4. Раздача фронтенда

Нужно решить один из двух вариантов (агент может предложить рекомендацию, но должен явно её обосновать):

- **Вариант А**: React собирается через Vite, бандл кладётся в Django `static/`, раздаётся через шаблон-обёртку Django — проще для старта, единый деплой
- **Вариант Б**: отдельное SPA за отдельным сервером/нгинксом, обращается к Django API по CORS — более гибко при росте, но сложнее в деплое сейчас

Рекомендация: начать с варианта А.

## 5. Доработки самого редактора (можно отдельным этапом, не блокирует интеграцию)

- Условное форматирование — цвет/иконка виджета меняются по порогу значения (авария/норма/предупреждение); сейчас цвет статичный, задаётся вручную в палитре цветов
- Множественный выбор и групповые операции над виджетами (сейчас можно выделить только один)
- Undo/redo
- Навигация между несколькими экранами — сейчас в прототипе один захардкоженный экран ("Котельная №1"), нужен список экранов и переключение между ними
- Расширяемая библиотека символов — насосы, клапаны, трубы в разных ориентациях и состояниях (десятки типов), палитра должна расти без переписывания кода
- Alarm-баннер / список активных аварий на экране

## 6. Не забыть

- Права доступа — кто может редактировать экраны, кто только просматривать в runtime-режиме
- Поведение при одновременном редактировании одного экрана двумя пользователями — как минимум предупреждение о конфликте, блокировка необязательна на первом этапе

## Приоритет реализации

1. Модель `Screen` + API CRUD (пункты 1–2)
2. Реальные теги в панели свойств вместо захардкоженного списка
3. Сохранение через API вместо console.log
4. WebSocket для живых данных вместо поллинга (пункт 3)
5. Раздача фронта (пункт 4)
6. Доработки редактора (пункт 5) — по мере необходимости, не блокируют базовую интеграцию
